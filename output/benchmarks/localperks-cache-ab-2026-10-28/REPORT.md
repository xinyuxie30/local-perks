# LocalPerks：仅 Redis 与 Caffeine + Redis 对照压测

正式样本为 3 轮 × 2 种配置 × 2 个场景。每场景每种配置独立重启、等布隆过滤器加载完成、预热 50,000 次请求，再测量 60 秒。以下为三轮中位数；未修改简历或业务代码。

## 聚合结果

| 场景 | 配置 | 完成 QPS 中位数（范围） | P50 / P95 / P99（ms） | Redis GET / HTTP请求 | L1 命中率 |
|---|---|---:|---:|---:|---:|
| 热点单商户，400并发 | 仅Redis | 7,561（7,350–7,858） | 50.4 / 62.8 / 101.2 | 1.000000 | 未启用 |
| 热点单商户，400并发 | Caffeine+Redis | 17,064（16,846–17,246） | 22.3 / 28.0 / 55.9 | 0.000000 | 100.00% |
| 混合商户，200并发 | 仅Redis | 7,667（7,211–7,763） | 25.2 / 31.5 / 50.1 | 0.920435 | 未启用 |
| 混合商户，200并发 | Caffeine+Redis | 13,939（13,801–13,983） | 14.0 / 17.9 / 28.9 | 0.122029 | 79.84% |

混合流量中 70% 访问热点池（100 家）、20% 访问长尾池（20,000 家）、10% 查询不存在 ID；QPS 包括正确返回的“不存在”，成功返回店铺数据的 QPS 单独保存在 results.json。闭环运行请求数不同，但使用同一确定性请求序列与分布。

- 热点场景：吞吐为 Redis-only 的 2.26 倍，P95 降低 55.4%，几乎消除热点 Redis GET（三轮累计 3,069,779 个 HTTP 请求，实例 GET 增量合计 3 次）。
- 混合场景：吞吐为 Redis-only 的 1.82 倍，P95 降低 43.2%，按每请求归一化的 Redis GET 减少 86.74%。

## 结果口径与证据

- 同一最终 JAR SHA-256：`9071ccfd4ede7ca37c0f4408b396dcf2b7a692b094e0c88e21d84ea11ad09a3f`；Nginx/Tomcat 长连接优化在两臂均开启。业务启动参数逐项比较，仅本地缓存开关不同（GC 日志文件名因轮次不同）。
- L1 容量 10,000、TTL 300 秒。已存在商户 L2 TTL 30 分钟；负缓存在正式测量前设为正常 120 秒。所有正式样本的商户表行读取增量为 0，比较的是预热后的读路径。
- 启用 L1 命中会跳过 Redis 布隆过滤器、Redis GET 及 JSON 反序列化；所以这是项目完整 L1 快速路径的收益，并非 Caffeine 和 Redis 单次操作的微基准。
- Redis GET 为实例计数；定时对账可能产生少量额外 GET。Redis EVAL、GETBIT 等命令增量完整保留，但脚本内部命令也计数，不能把它们简单相加当作网络请求数。
- Caffeine 命中率使用测量窗口的 hit/miss 差值，Redis-only 的空统计不解释为 100% 命中；混合场景命中率分母包含不存在 ID。
- 8,298,189 个正式 HTTP 请求已从 gzip NDJSON 原始记录独立重计，核对数量、状态、业务结果、连续唯一序号及 P95（0.1ms 桶精度）；12 个样本均无异常、无丢弃、无监控错误。
- 这是单机短时缓存容量对照，压测器、Nginx、Java、数据库和 Redis 共享主机资源。不能外推生产整体吞吐、冷启动、失效风暴或分布式缓存一致性。系统/应用 CPU、客户端 CPU/事件循环延迟、Redis CPU 和剩余资源保留在 results.json 及 telemetry。
- 未改持久化策略；未新增订单。结束状态已恢复 L1 开启，详情见 complete.json。原应用日志、启动参数、每次预热和正式测试的 before/after 快照及原始请求均保留。

## 使用边界

此前约 1,900→13,450 QPS 的测试，两边都已启用本地缓存，主要反映连接复用等配置修复。本报告固定这些配置，只比较 L1 开/关；两组收益不能相乘，也不能合并成一次性能提升。
